# UI 与美术规范

## 核心目标

Parti Room 首先应让玩家感受到“这是一个游戏界面”，而不是后台、表单或普通长网页。

通用优先级：

- 游戏感优先于网页感；
- 主界面尽量完整呈现在当前视口；
- 移动端触控优先；
- 核心状态尽量视觉化；
- 重要操作有明确反馈；
- 空间不足优先重新布局，而不是无限增加页面高度。

这些是设计建议，不是需要逐条自动化证明的验收标准。

## 主界面与响应式

推荐基础：

```css
html,
body,
#app {
  width: 100%;
  height: 100%;
  margin: 0;
}

body {
  min-height: 100dvh;
  overflow: hidden;
  overscroll-behavior: none;
  touch-action: manipulation;
}
```

空间不足时可以：

- 缩减低优先级文字与装饰；
- 调整元素大小与间距；
- 切换布局方向；
- 使用分页、弹层、抽屉或缩略视图；
- 针对手机、横屏、平板和桌面做不同布局。

不要求针对大量固定分辨率建立自动测试矩阵。开发者挑选几个有代表性的设备或浏览器实际试玩即可。

## Safe Area

需要注意移动设备安全区，以及 Parti 全屏时右上角宿主控件可能占用的区域。

例如：

```css
.game-shell {
  padding-top: env(safe-area-inset-top, 0px);
  padding-left: env(safe-area-inset-left, 0px);
  padding-bottom: env(safe-area-inset-bottom, 0px);
  padding-right: max(88px, env(safe-area-inset-right, 0px));
}
```

关键按钮不要固定在可能被宿主控件遮挡的位置。

## 游戏化表达

有天然实体概念时，优先把状态表现成可理解的游戏对象、图标、轨道、场景元素或玩家区域，而不是只使用：

```text
状态文本
输入框
下拉框
提交按钮
数据表格
```

如果使用 LittleJS，Canvas 场景同样应直接表达游戏状态，而不是只作为普通网页背景。

## 交互反馈

玩家操作后应有及时、明确的反馈。

常见状态可以包括：

```text
pressed
selected
locked
disabled
resolved
error
```

不要求每种状态都建立自动截图或视觉回归测试。只要开发者和玩家在实际试玩中能清楚理解当前状态即可。

## 动画

动画用于解释状态变化，不应拖慢玩法。

Worker 决定规则结果，UI 或 LittleJS 负责表现结果。支持 `prefers-reduced-motion` 是推荐项，但不应为了动画验证建立复杂测试体系。

## DOM / 场景更新

避免每次 snapshot 都销毁整个 UI：

```ts
app.innerHTML = renderEverything(state);
```

更推荐只更新发生变化的部分，以避免破坏 focus、拖拽、pointer capture 等交互状态。

LittleJS 场景也应更新已有模型和对象，不要因为每次 snapshot 都重新初始化整个引擎。

## 美术完整度

不要求高成本原创美术，但建议保持：

- 主题色和视觉语言统一；
- 图标风格一致；
- 重要状态有明显区分；
- 背景、面板和核心对象有基本层级；
- 发布版本不要直接呈现成默认后台模板或白底表单页面。

## 游戏封面

**正式上线的 Room 必须提供封面。** 封面用于在 Parti 的列表、市场或其他入口中让玩家快速识别游戏，不应使用空白占位图或临时开发截图代替正式封面。

根据复杂度选择最简单的制作方式：

- **简单封面**：可以直接使用 SVG 自行绘制，适合几何图形、图标、标题排版和简单构图；
- **复杂封面**：可以使用生图工具生成，再进行必要的裁切、排版和压缩；
- 如果使用生图工具，最终交付文件应使用 **JPG** 格式；
- **复杂 JPG 封面文件大小必须不超过 200 KB**；
- 优先保证缩略图状态下仍能辨认主体和标题，不需要为了封面制作建立复杂的自动视觉验证流程。

封面属于正式发布资产。开发阶段可以暂时没有，但准备上线时必须补齐。

## 性能

优先保证手机上实际可玩：

- 避免无必要的大图和大量资源；
- 动画优先使用合适的 GPU 友好属性；
- 不在每个 snapshot 全量重建 DOM；
- Canvas / WebGL / LittleJS 项目根据实际设备控制分辨率和对象数量。

性能判断也应以实际试玩为主，不要求默认建立自动 benchmark。

## 视觉验证原则

视觉和交互验收主要交给开发者与玩家。

推荐做法：

1. 在 Parti 中打开实际 Room；
2. 用手机和桌面至少各体验一次；
3. 完成核心操作；
4. 观察是否有遮挡、难点、误触或难以理解的反馈；
5. 根据试玩直接调整。

AI 可以帮助检查 CSS、DOM 结构、明显溢出风险和代码问题，但**不应默认依赖 AI 截图分析、逐分辨率视觉比对或自动视觉评分来判定 UI 是否正确**。这类验证成本高，而且不能替代真实玩家对可玩性和体验的判断。

## 最小 UI 验收

发布前由真人确认即可：

- [ ] 核心操作可以完成；
- [ ] 手机上没有明显不可用或被遮挡的问题；
- [ ] 桌面上布局基本合理；
- [ ] 玩家能理解当前该做什么；
- [ ] 主要操作有可感知反馈；
- [ ] 正式上线版本已经提供封面；
- [ ] 复杂封面使用 JPG，且文件大小不超过 200 KB。

其他视觉与体验细节按项目需要迭代，不作为 quick-start 的默认硬性约束。
